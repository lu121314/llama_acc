# 在另一块同型号 ZU7CG / PYNQ 4.0 板卡部署网页推理工程

本指南适用于将本工程复制到另一块**同型号、同器件与同 DDR 布线的 ZU7CG 板卡**，并使用该板的 PYNQ 4.0 镜像。本次保留原有器件、HWH 接口和固定地址约束，不把运行库扩展为通用 FPGA 驱动。网页界面通过电脑浏览器访问，不需要板卡连接显示器、安装桌面或安装浏览器。先确认硬件和内存布局，再安装 Python 依赖、检查资源，最后下载 Overlay 和上传权重。

## 1. 先判断新板卡是否能使用这套加速器

PYNQ 4.0 是软件运行条件，不代表不同板卡可以使用同一个 bit。当前加速器是 Zynq UltraScale+ MPSoC 的双核、PS DDR + 独立 PL DDR 设计，运行库依赖 `DataPath_Pynq` 的寄存器协议、17 位 token ID、四路 PS HP AXI 通道，以及 PS 能访问的 PL DDR 窗口。

| 新板卡情况 | 需要完成的工作 |
|---|---|
| 与原 ZU7CG 板卡型号、器件封装、板级连线、DDR 和时钟完全一致 | 核对镜像及启动配置后，可使用对应构建的 bit/HWH/manifest |
| 同为 ZU7CG，但 DDR 型号、容量、引脚或参考时钟不同 | 根据新板原理图、DDR 参数和时钟重新生成硬件；不能只替换板卡名称 |
| 其他 Zynq UltraScale+ MPSoC 型号，即使具有独立 PL DDR | 不在本次支持范围；需要另行移植硬件和运行库 |
| 仅有 PS DDR，没有本工程使用的独立 PL DDR | 当前双 DDR 版本不能直接部署，需另外设计硬件和数据布局 |
| Zynq-7000、不同处理器架构或不兼容的控制协议 | 不能仅复制 Python 工程运行，需要单独移植硬件与驱动 |

这里的“新板”仅指另一块与原板硬件兼容的同型号板卡。SD 卡、网络 IP、主机名、工程目录和 PYNQ venv 路径可以不同；器件、DDR 布线与硬件地址映射必须匹配。本次不提供修改器件或任意地址的配置模板。

新板硬件仍需遵循本工程控制协议。原裸机 `DataPath_xN` 将 PS 模型放在低地址 `0x36000`，该区间与 Linux 使用的内存重叠；它在本运行库中只允许受限诊断，不能作为 PYNQ 推理版本。不要通过删除检查将它强行用于 Linux。

当前发布的 ZU7CG 硬件对应器件 `xczu7cg-ffvc1156-1-e`。器件不同，或者虽器件相同但板级连接不同，都不能用本次软件更新直接适配。配置中的器件和固定地址检查继续保留；修改它们不会改变已经编译到硬件中的连线。

## 2. 准备新板资料

开始适配前，保留以下资料。它们用于确定配置，避免在未知物理地址上试写模型：

| 资料 | 需要记录的内容 |
|---|---|
| 板卡型号 | 厂商、板卡名称、硬件修订版 |
| FPGA 器件 | 完整 part，包含型号、封装与速度等级 |
| PYNQ 镜像 | PYNQ 版本、板级镜像来源、Linux/Ubuntu 版本、CPU 架构 |
| PS DDR | 物理容量、Linux 运行设备树中的实际地址分段、可供模型预留的区域 |
| PL DDR | 是否存在、容量、DDR 器件型号、引脚和参考时钟、MIG 参数 |
| 地址映射 | CPU 控制窗口、CPU 到 PL DDR 窗口、加速器到 PS/PL DDR 的地址映射 |
| 时钟与复位 | 加速器目标时钟、DDR 时钟、复位来源及极性 |
| 硬件交付 | 同次导出的 bit、同名 HWH、manifest；时序与资源报告 |
| 模型交付 | 模型版本、量化/打包格式、1K 或 8K 上下文、每核镜像大小和 tokenizer |
| 启动结构 | SD/eMMC 启动介质、实际 DTB/FIT、extlinux/U-Boot 配置和可恢复的原镜像 |

在新板 Jupyter 终端，以下命令只读取信息。每个代码框作为一整条命令执行：

```bash
cat /etc/os-release; uname -m; uname -r; dpkg --print-architecture
```

```bash
cat /proc/cmdline; lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS; ls -lah /boot; ls -lah /boot/firmware 2>/dev/null
```

```bash
hostname -I; free -h; df -h /home /tmp /boot; command -v cc; command -v gcc
```

不要将另一块板卡的 `BOOT.BIN`、整份 DTB 或 Linux 镜像直接覆盖到新板。新板启动环境应由该板卡的适配镜像提供。

## 3. Python 环境与权限

本工程当前验证环境是 PYNQ 4.0.x、Linux arm64/aarch64、Python 3.12。启动脚本依次选择显式 `PYNQ_PYTHON` / `LLAMA_PYTHON`、当前已激活的 venv、标准 PYNQ venv，最后使用 `python3`。显式指定的解释器不存在时会报错。原板的标准 PYNQ venv 路径为：

```text
/usr/local/share/pynq-venv/bin/python3
```

先确认该解释器及 PYNQ 可用：

```bash
/usr/local/share/pynq-venv/bin/python3 -c 'import sys,platform,pynq; print("Python:",sys.executable,sys.version); print("CPU:",platform.machine()); print("PYNQ:",pynq.__version__)'
```

不要因为系统存在 `python3`，就认定它和 Jupyter 使用同一个虚拟环境。在已有的其他 PYNQ venv 中运行时，指定该环境解释器。例如：

```bash
PYNQ_PYTHON=/实际路径/venv/bin/python3 bash run.sh --mode ui
```

日常运行需要 `transformers` 及其 tokenizer 依赖，本地权重计算由 FPGA 完成，不要求为 tokenizer 安装 PyTorch、TensorFlow 或 Flax。提示“未发现 PyTorch/TensorFlow/Flax”本身不代表 tokenizer 不可用；应以资源检查是否通过为准。

联网板卡可在工程目录使用同一个解释器安装工程依赖：

```bash
/usr/local/share/pynq-venv/bin/python3 -m pip install -r requirements.txt
```

离线板卡使用与 **arm64、Python 3.12、当前 Linux ABI** 匹配的离线 wheel 包，复制到板卡后，在同一个 venv 中执行 `pip --no-index --find-links` 安装。不要复制电脑上 x86_64 的虚拟环境，也不要直接使用 Windows 或其他 Python 小版本的二进制包。已安装可用依赖时不必重装整个环境。

若已准备好本工程依赖的完整离线 wheel 目录，例如 `updates/wheels/`，可在工程目录执行：

```bash
/usr/local/share/pynq-venv/bin/python3 -m pip install --no-index --find-links updates/wheels -r requirements.txt
```

此目录需要包含依赖本身及其传递依赖的匹配 wheels；已有专用离线补丁时优先遵循该补丁的说明。

板卡还需要 `cc` 或 `gcc`。运行库首次上传 DDR 时会在临时目录编译一个很小的本机对齐拷贝模块；不需要板卡安装 Vivado。上传使用 `/dev/mem`，配置 PL 也需要相应系统权限。当前部署从具有 root 权限的 Jupyter 终端运行；若新板 Jupyter 用户没有这些权限，应按该板的 PYNQ 权限配置运行，不能跳过物理内存检查。

完成工程复制后，可用只读环境检查工具采集新板信息。指定实际使用的 PYNQ venv；下例使用原板标准路径：

```bash
/usr/local/share/pynq-venv/bin/python3 tools/check_board_environment.py --config config/pynq.json
```

该工具报告 Python/PYNQ、CPU 架构、内存、运行设备树的模型预留和资源状态；它不会下载 bit、写 DDR 或修改启动文件。工具退出码 0 和 `config.valid=true` 只表示配置可解析，不表示板卡、硬件和模型均已通过验收。资源未准备完整时，可先保留输出作为待配置清单，再继续下面步骤。

## 4. 复制工程与放置硬件文件

本指南以主部署工程 `llama32_3b_zu7cg_pynq_v1` 为例；独立 8K 工程的 `config/pynq.json` 默认仍为 8192。建议每块板保留一份独立工程，在工程内部用配置与硬件子目录区分上下文和时钟组合。例如：

```text
/home/xilinx/jupyter_notebooks/<项目目录>/
├── run.sh
├── run_ui.sh
├── llama32_pynq/
├── ui/
├── config/
├── hw/
│   ├── <overlay>.bit
│   ├── <overlay>.hwh
│   ├── manifest.json
│   ├── ctx8192/              8K 硬件的独立目录，等待对应交付
│   └── idle/                 可选：与本板器件匹配的空闲 bit
├── data/
│   ├── core0.bin             PS DDR 镜像
│   ├── core1.bin             PL DDR 镜像
│   ├── model_manifest.json
│   ├── ctx8192/              8K 的 core0.bin/core1.bin/model_manifest.json
│   └── tokenizer/
├── test/
└── logs/
```

bit 与 HWH 必须同名并放在同一个目录；`manifest.json` 放在这对文件的目录中。三者需要来自同一次、同一硬件构建。不能将 187.5 MHz 的 HWH 与 250 MHz 的 bit 混用，也不能用修改 manifest 哈希的方式掩盖不匹配。manifest 的配套校验不等于已经证明新板的 DDR、引脚、时序和推理正确。

如果本次只提供了网页软件、尚未提供新板 bit/HWH，则可以使用 `--demo` 检查网页，但不要把当前 ZU7CG bit 下载到不同器件。8192 上下文的软件选项也需要等待匹配的 8K 硬件文件，不能仅因界面出现选项就认为硬件可运行。

HWH 校验继续依赖当前加速器、PS、PL DDR、复位与 AXI 实例的接口关系。同型号新板应使用同一协议和兼容的实例结构；本次不会放宽这些校验来接收其他器件或不兼容工程。

“清除 bit”使用独立空闲 bit。它同样与 FPGA 器件绑定；新板必须提供该器件可用的空闲配置。没有匹配的空闲 bit 时，先使用正常初始化与推理流程，待补齐空闲 bit 后再验证清除演示。

### 四个网页选项及文件对应关系

| 网页组合 | 配置文件 | bit 文件 | 模型目录 |
|---|---|---|---|
| 1024 context / 187.5 MHz | `config/pynq.json` | `hw/llama32_3b_zu7cg_pynq_v1.bit` | `data/` |
| 1024 context / 250 MHz | `config/pynq_250m.json` | `hw/250m/llama32_3b_zu7cg_pynq_250m_v1.bit` | `data/` |
| 8192 context / 187.5 MHz | `config/pynq_ctx8192_187m5.json` | `hw/ctx8192/187m5/llama32_3b_ctx8192_187p5mhz.bit` | `data/ctx8192/` |
| 8192 context / 250 MHz | `config/pynq_ctx8192_250m.json` | `hw/ctx8192/250m/llama32_3b_ctx8192_250mhz.bit` | `data/ctx8192/` |

每个 bit 旁放同名 `.hwh` 和该组合自己的 `manifest.json`。模型目录各放 `core0.bin`、`core1.bin`、`model_manifest.json`；四个选项共用 `data/tokenizer/`。本次软件更新保留两个 8K 选项和路径，**不代填 8K 硬件文件**。资源未交付时选项显示待交付并禁止初始化，不会偷偷改用 1K 的 bit 或模型。

同一上下文下，两种时钟可共用相应打包模型；1K 与 8K 镜像不共用。将后续 8K 硬件和镜像放入上述位置后，重启 UI 服务，再运行对应配置的资源检查。

### 配置字段

配置路径以工程根目录为基准，因此可更换工程目录名，不必保留原来的绝对路径。主要字段如下：

| 字段 | 用途 |
|---|---|
| `bitfile` | 当前组合的 bit 相对路径；HWH 和硬件 manifest 由同目录推导 |
| `model_ps` / `model_pl` | 对应上下文的两核镜像路径 |
| `tokenizer` | 本地 tokenizer 目录 |
| `model_manifest` | 对应上下文的数据布局说明路径 |
| `context_tokens` | 仅支持 1024 或 8192，与硬件和模型同时匹配 |
| `image_bytes` | 每核镜像字节数，随上下文确定，不是任意调整的内存容量 |
| `layout_id` | 1K 为 `0x32334232`，8K 为 `0x3342384b` |
| `clock_hz` | 187500000 或 250000000，须与 HWH 的实际时钟一致 |
| `project_name` | 硬件构建标识，须与相应硬件 manifest 一致；不因复制目录而随意改名 |
| `variant_id` | 网页中该配置组合的标识 |
| `timeout_s` / `poll_interval_s` | 原有等待时间与轮询周期 |
| `chunk_bytes` | 权重分块上传大小；必须保持为正数且按 4096 字节对齐 |

`part`、`control_base`、`ps_base`、`ps_size`、`ps_logical_base`、`pl_base`、`pl_size` 继续使用当前固定合同，不能作为新板任意改地址的入口。IP 和 hostname 由板卡网络决定，UI 监听地址和端口由启动参数决定，不写入 FPGA 地址配置。

## 5. 核对地址和模型容量

本次支持的同型号 ZU7CG 使用以下**固定硬件地址**。这些地址不是适用于所有 PYNQ 板卡的统一分配方案：

| 用途 | CPU 物理起始地址 | 区域大小 |
|---|---|---|
| PS DDR / core0 模型池 | `0x800000000` | `0x80000000`，2 GiB |
| PL DDR / core1 CPU 窗口 | `0x400000000` | `0x100000000`，4 GiB |
| 加速器控制 | `0x500000000` | 软件只映射 4 KiB 控制页 |

当前 HWH 的 AXI-Lite 地址窗口较大，运行库只映射需要的 4 KiB；不要为整个 HWH 窗口分配同等大小的内存。PL DDR 的 CPU 窗口来自硬件 AXI 映射，不需要从 Linux PS DDR 或 CMA 再分配 4 GiB。加速器访问 PL DDR 的 AXI 地址可从 0 开始，和 CPU 看到的物理窗口不同，以 HWH 中的两侧映射为准。

本工程当前两个模型布局：

| 上下文容量 | 每个 `core*.bin` 的大小 | 两核镜像合计 | 当前 PS 2 GiB 池是否容纳 |
|---|---|---|---|
| 1024 token | 1,427,628,032 字节（`0x5517e000`） | 2,855,256,064 字节 | 是 |
| 8192 token | 2,063,458,304 字节（`0x7afde000`） | 4,126,916,608 字节 | 是，剩余约 80.13 MiB |

两份镜像分别放在 PS 和 PL DDR，不是一起塞入 PS 的 2 GiB 池。镜像包含与上下文相关的布局，不能让 8K 硬件沿用 1K 镜像，也不能仅修改 Python 中的上限将 1K 硬件变成 8K。

上限表示 **system prompt、chat 模板、当前输入、历史和预留输出的总 token 数**。中文字符数不等于 token 数；输入可能未超上限，但加上最大输出及历史后仍会超限。出现预算不足时，可以减少最大输出或开始新对话。Chat 每轮会重新提交完整历史；Prompt 模式不携带前面的对话。运行库的精确预算为 `输入 token 数 + 最大输出 token 数 - 1 <= context_tokens`，因为最后一个输出不再作为下一次输入提交。

本次不支持在 JSON 中另填一组 PS/PL 地址。若目标板必须更改地址，就属于新的硬件移植任务，需要硬件与运行库共同设计；不要把它作为普通部署设置修改。

## 6. 在启动设备树中预留 PS 模型池

该预留的目的是在 Linux 开始分配内存前，排除加速器要直接写入的 PS 模型区域。虚拟环境、增加 swap、`pynq.allocate()`、增大 CMA 或运行时加载 DT overlay 都不能代替启动时的专用 `no-map` 预留。

先确认新板真实物理 RAM 地址，以及启动使用的是独立 DTB、FIT 的 `image.ub`，还是经 U-Boot 脚本选择的其他文件。`/boot/system.dtb` 存在，不代表它正在生效。若是 extlinux，应读取实际使用的 `extlinux.conf` 中 `fdt` 或相关引用；若 DTB 位于 FIT 中，需要按该板镜像构建流程重新制作 FIT。

下面 Python 代码只读运行中的设备树，可在 Jupyter Notebook 单元执行。它不会下载 bit、写 DDR 或修改启动文件：

```python
from pathlib import Path

root = Path('/sys/firmware/devicetree/base')
nodes = [root] + sorted(root.glob('memory*'))
reserved = root / 'reserved-memory'
if reserved.is_dir():
    nodes += [reserved] + sorted(p for p in reserved.iterdir() if p.is_dir())
for node in nodes:
    print('\nNODE:', node)
    for name in ('#address-cells', '#size-cells', 'device_type', 'reg', 'ranges',
                 'no-map', 'reusable', 'compatible', 'status', 'size',
                 'linux,cma-default', 'linux,dma-default'):
        prop = node / name
        if prop.is_file():
            value = prop.read_bytes()
            print(name, value.hex(' ') if value else '<empty>')
```

对于本次同型号硬件，仍需确认新板对应高地址 RAM 真实存在，并且根节点的地址及大小 cells 都为 2；满足这些条件时，以下才是相应节点示例。它是**合并到新板设备树的片段**，不是覆盖整份设备树的文件：

```dts
/ {
    reserved-memory {
        #address-cells = <2>;
        #size-cells = <2>;
        ranges;

        llama32-ps@800000000 {
            reg = <0x00000008 0x00000000 0x00000000 0x80000000>;
            no-map;
        };
    };
};
```

该节点是专用物理区，不添加 `reusable`、`shared-dma-pool`、CMA 或 DMA 默认池标记。目标区必须完整位于真实 PS RAM 中，不能与其他预留重叠。若板卡已有旧版本模型池，先确认归属再迁移；不要保留旧池又叠加新池，导致 Linux 可用内存不足。

实际修改流程是：备份启动介质和原配置 → 基于已确认的活动设备树合并预留 → 编译到新文件 → 核对地址和其他节点仍保留 → 修改已确认的启动引用 → 重启。修改前保留串口或 SD 卡恢复途径。不同板卡启动结构不同，本工程不提供一个自动覆盖所有板卡 `/boot` 的命令。

重启后，必须读取 `/sys/firmware/devicetree/base` 的**运行设备树**验收。当前参考布局在工程目录执行：

```bash
/usr/local/share/pynq-venv/bin/python3 -c 'from llama32_pynq.memory import assert_ps_reserved; print(assert_ps_reserved())'
```

本次同型号布局预期输出 `base=34359738368`、`size=2147483648`、`no_map=True`。如果新板缺少这一物理区，或容量不满足要求，则不能继续按本指南部署。只看到磁盘 DTB 中有节点，或者 `free -h` 变小，都不能替代该检查。预留检查失败时先修正启动配置，不进入权重上传。

## 7. 模型与 tokenizer

复制与所选硬件上下文一致的 `core0.bin`、`core1.bin` 和 `model_manifest.json`。保留两核顺序：core0 对应 PS，core1 对应 PL。HF 原始 `.safetensors` 文件不能直接当作这两份镜像；需要使用本工程兼容的量化和双核打包导出结果。

`data/tokenizer/` 至少应包含 `tokenizer.json` 及配套 tokenizer 配置和 chat template。当前模型是 Llama3.2-3B，使用 128256 词表、BOS=128000、EOS={128001,128008,128009}。模型和 tokenizer 需要配套，不能替换为 Llama2 分词器。

网页支持 UTF-8 多语言输入输出，实际语言能力由本地模型决定；不调用在线翻译服务。新板离线运行时，只需复制完整本地 tokenizer，不需要从 Hugging Face 下载权重。

检查存储空间时同时考虑工程、两份镜像、bit 和日志；不要把多 GiB 权重复制到容量不足的 `/tmp`。重启或断电会丢失 DDR 中的模型，磁盘镜像仍在，下一次初始化重新上传即可。

## 8. 首次部署验证

先停止旧 UI、Notebook 或其他正在访问同一加速器的进程。一个服务可连接多个浏览器；不要同时启动多个独立硬件控制进程。

在新板工程目录，先运行不访问硬件的资源检查：

```bash
/usr/local/share/pynq-venv/bin/python3 -m llama32_pynq check
```

需要指定配置时，按诊断入口的参数顺序执行。下例是当前 1K 187.5 MHz 配置；检查其他组合时换成对应配置文件：

```bash
/usr/local/share/pynq-venv/bin/python3 -m llama32_pynq --config config/pynq.json check
```

8K 187.5 MHz 组合交付完整后，检查例子：

```bash
/usr/local/share/pynq-venv/bin/python3 -m llama32_pynq --config config/pynq_ctx8192_187m5.json check
```

预期 `inference_assets_ready=true`、`overlay_manifest_verified=true`、`tokenizer_verified=true`，且 `inference_blockers` 为空。检查失败时处理缺失文件、模型大小或硬件配套问题；不要手动删掉断言后继续。

已确认硬件与地址匹配、PS 预留生效后，运行寄存器与双 DDR 小范围读写恢复测试：

```bash
/usr/local/share/pynq-venv/bin/python3 -m llama32_pynq --config config/pynq.json probe --ddr-test
```

该操作会下载 Overlay，并对两个模型池末页进行小范围写入、读回和恢复。它不是只读资源检查，也不是完整内存容量测试。新板地址未确认前不要执行。

随后使用普通文本测试，而非将 BOS-only 用例当作唯一金标准：

```bash
bash test/run_terminal_validation.sh --skip-bos --prompt 'Explain what an FPGA is.' --max-new-tokens 16
```

```bash
bash test/run_same_session_repeat.sh --prompt 'Explain what an FPGA is.' --max-new-tokens 16
```

```bash
bash test/run_two_prompts.sh --prompt-1 '请用中文解释 FPGA。' --prompt-2 'What is a CPU?' --max-new-tokens 32
```

主部署工程的上述脚本默认检查 1K 187.5 MHz，支持 `--config` 指定其他组合；本独立 8K 工程继续使用自身默认配置，原脚本参数以 `--help` 为准。主工程 8K 文件交付完整后，例如：

```bash
bash test/run_same_session_repeat.sh --config config/pynq_ctx8192_187m5.json --prompt 'Explain what an FPGA is.' --max-new-tokens 16
```

诊断脚本会进行权重哈希与 DDR 回读，速度比日常上传慢；它们保留详细日志和 JSON，适合首次验收。日常 UI 不做权重哈希或回读，仅显示上传进度和速度。

已有版本的 BOS-only 用例存在已局部复现的状态残留问题，跳过该用例不等于问题已修复。新板至少记录普通文本首次生成、同一进程软复位后同 prompt 的逐 token 对比，以及不同 prompt 的结果。合理文本输出是功能抽查，通过一次不代表已经完成模型数值精度验收。

## 9. 启动网页并点击终端地址

以下以原工程目录名为例。复制到其他目录时替换 `cd` 后的路径：

```bash
cd /home/xilinx/jupyter_notebooks/llama32_3b_zu7cg_pynq_v1 && bash run.sh --mode ui
```

成功绑定端口后，终端会打印 `http://<板卡IP>:8088/`。在电脑的 Jupyter 终端点击这个完整地址；部分终端需要 `Ctrl+单击`。也可复制到电脑浏览器。不要将 `0.0.0.0` 当作访问地址，也不要从电脑打开它自己的 `127.0.0.1`。如果打印多个板卡网卡地址，选择电脑能访问的那个。

终端保持运行，按 `Ctrl+C` 停止。默认网页是 HTTP；手动改成 HTTPS 不会启用加密服务。更改端口的例子：

```bash
bash run.sh --mode ui --port 8090
```

仅预览网页时：

```bash
bash run.sh --mode ui --demo
```

模拟模式不会访问 FPGA，也不能证明硬件或权重已就绪。网页的硬件选项会同时标注上下文容量和时钟。核对所选的 1024 或 8192 context，以及 187.5 或 250 MHz；尚未交付 bit/HWH/manifest 的 8K 组合显示待交付，不能初始化，也不会自动回退到 1K。点击已具备完整资源的组合进行初始化，界面会依次显示文件检查、硬件下载、双 DDR 权重上传和就绪状态。进度条显示百分比、累计 MiB、MiB/s 与耗时。

输入 prompt，设置最大输出，选择 Prompt 或 Chat。顶部显示输入/输出 token 数、首 token 延迟、总生成耗时、解码 token/s、包含输入处理的总体 token/s 和停止原因；右侧实时打印运行日志。首 token 延迟包含 prefill，完整历史更长时可能增加。

“清除 bit”是空闲时加载匹配器件的空闲配置，移除当前加速器，之后需重新初始化和上传权重。它不删除磁盘上的 bit、HWH 或模型，也不用于正在超时或仍有事务时的强制恢复。使用前先确认空闲 bit 已为新板准备并验证。

## 10. 常见问题

| 现象 | 检查与处理 |
|---|---|
| `No module named pynq` | 检查 `PYNQ_PYTHON` 是否指向装有 PYNQ 4.0 的板卡 venv；不要默认使用系统 Python |
| `No module named transformers` | 在同一个 PYNQ venv 安装匹配的 tokenizer 依赖；离线时使用对应 arm64/Python 版本的 wheels |
| 提示未发现 PyTorch/TensorFlow/Flax | 本工程只在 CPU 上使用 tokenizer，先看 tokenizer 检查是否通过，不必为该提示安装大型框架 |
| 缺少 `cc` 或 `gcc` | 按新板系统安装编译器，或准备匹配系统的离线安装包，再运行 DDR 上传 |
| bit 器件不匹配 / HWH 校验失败 | 使用新板对应构建的 bit、同名 HWH 和 manifest；检查器件、地址、实例结构、复位与时钟 |
| PS 模型池不是专用 `no-map` | 核查实际启动 DTB/FIT 和运行设备树，修正并重启；不要通过增大 CMA 或跳过检查处理 |
| 模型镜像大小错误 | 核对 1K/8K 选项、量化打包版本和两核镜像，原始 HF 权重不能直接上传 |
| `Permission denied` / `/dev/mem` 不可用 | 检查运行权限和该板内核的物理内存访问支持，不改写为 Linux 正在使用的其他地址 |
| `Address already in use` | 旧 UI 可能仍在运行；返回旧终端 Ctrl+C，或使用另一个端口。硬件推理只保留一个控制服务 |
| 终端打印地址但电脑无法打开 | 检查电脑与板卡网段、所选网卡地址和端口是否可达；确认使用 HTTP，服务终端仍在运行 |
| Notebook 内 iframe 空白 | HTTPS Jupyter 可能阻止 HTTP 嵌入；直接用终端打印地址在浏览器新标签页打开 |
| 输入加输出超过硬件上下文 | 减少最大输出、缩短输入或开始新 Chat；使用 8K 需配套 8K 硬件和模型，不只改 UI 限制 |
| 上传后首 token 等待较长 | 查看右侧阶段日志；首 token 包含 prefill。区分上传总耗时与真正生成耗时，保留出错日志后排查 |
| 断电后模型不再就绪 | 重新启动服务、初始化并上传两份权重。磁盘镜像仍在时不用重新复制模型文件 |

## 11. 新板验收记录

每块新板保存一份自己的记录，不复用旧 ZU7CG 的“通过”结论：

- 板卡型号、器件、PYNQ/Python 版本和启动镜像来源。
